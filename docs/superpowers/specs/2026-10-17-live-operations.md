# FraudLens live operations design

The approved scope is a complete local showcase for UPI, net banking, card payments, and ATM withdrawals. Detect supported patterns, automatically request reversible protective restrictions, let authenticated analysts investigate and confirm fraud or mark false positives, and keep all console surfaces consistent. External bank integration is deferred. All transactions and banking operations in the showcase are explicitly simulated; no prevention or compliance claims extend beyond tested scenarios.

Keep Python/FastAPI, existing scoring components, and Next.js/React. Use SQLite with explicit transactions, WAL, foreign keys, unique event identifiers, optimistic case versions, and a durable delivery queue. The simulator is a separate FastAPI process with its own database. Background work runs in the API process; one worker per deployment is the supported local configuration.

New `/ops` endpoints are the authoritative operational interface. Historical preloaded demonstrations remain available only through documented legacy endpoints; the new console routes all use `/ops`, never mix legacy metrics with operational data. The landing page and documentation must make that boundary clear.

Transactions are attempted payments in integer paise. Record account, channel, amount, instrument where applicable, beneficiary, device, location, timestamp, authentication failures, and novelty signals. A deterministic transaction id enforces idempotency; conflicting reuse returns 409. Score from previously observed history plus the current event, never future transactions or the simulation's ground-truth labels. Retain existing rule/graph/behavioral/velocity/ML signals where appropriate; report synthetic ML limits explicitly. Channel controls remain transparent, versioned rules. The benchmark must evaluate all supported scenarios, benign activity, and false positives, without presenting synthetic results as real-bank validation.

Case state: `new`, `investigating`, `escalated`, `resolved`. Verdict: `unreviewed`, `fraud`, `false_positive`. Releasing protection is separate from resolving an investigation. A fraud confirmation with a confirmed restriction can resolve a case; a false-positive decision queues release and only resolves once release is confirmed. Optimistic versions reject concurrent stale decisions. Analyst identity comes from authentication.

Bank actions: `restrict` or `release`, target `account` or `card`, and status `pending`, `confirmed`, `failed`, or `superseded`. Every restriction is owned by a case; releasing one never clears another case's restriction. Preserve idempotency across timeout, retry, restart, and duplicate clicks. Requests are stored before delivery, successful acknowledgements are recorded before showing success, and retries reconcile uncertain outcomes. High-risk payments are not submitted before pending protective action is reconciled. The simulator declines subsequent attempted payments covered by an active restriction and posts allowed payments exactly once.

The console uses one live snapshot with a monotonic event cursor. Authenticated fetch streaming (or authenticated polling with cursor recovery) refreshes the same source for all views, with stale/disconnected state visible. Includes overall and per-channel transaction/case counts, a prioritized queue, evidence detail and network, bank ledger/actions, audit history, reports, scenario controls, and supported-guidance matrix. Reports are timestamped snapshots, with JSON and human-readable export.

Visual direction: a precise forensic operations workspace. Preserve emerald identity, use quiet neutral surfaces and readable spacing; risk colors carry meaning. Signature view is an incident timeline linking payment attempts, restriction acknowledgement, and analyst decisions. Responsive, keyboard usable, visible focus, loading/empty/error/disconnected states, and reduced-motion support are required. No invented customers, financial savings, real-bank connectivity, or compliance badges.

Protect operational reads and writes with backend bearer authentication; bank endpoints require an internal simulator key. Strict input models and bounded queries. Keep secrets out of committed files. Persistent signing secrets survive restart; non-demo startup must reject development credentials. Demo accounts are explicitly local-only. No external-bank calls, emails, account signup, deployment, push, or merge are authorized by this implementation request.

Delivery: working source, reproducible setup/start scripts, sample scenarios, test and evaluation results, architecture/limitations, source-linked guidance applicability matrix, screenshots, and a Git patch/archive. Regulatory source rows distinguish implemented controls from unverified applicability; formal NPCI approval and regulatory certification are not claimed.
